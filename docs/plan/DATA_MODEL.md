# Data model (PostgreSQL 18)

This is the source of truth for the schema. Migrations must produce exactly this, including every CHECK, foreign key, trigger and index. Each table lists the milestone that creates it. Decisions behind the shape are in `DECISIONS.md`; the HTTP view of these entities is in `API_CONTRACT.md`.

## 1. Global rules

| Rule | Detail |
|---|---|
| Money | `bigint` integer cents, in every table. PHP uses `int`; never `float` or `decimal`. A Pest arch test bans `float` in `app/Actions`, `app/Domain`, `app/Reports` and `app/Support/Money`. |
| Signed ledger | `transactions.amount_cents` is the **signed effect on the account balance**: expense < 0, income > 0, transfer legs ±, adjustment = delta (≠ 0). Every other `*_amount_cents` / `amount_cents` column (transfers, drafts, templates, budgets) is an **unsigned magnitude**. |
| Movement dates | `date` type, interpreted in `Europe/Madrid`. Never `timestamp`. |
| Timestamps | `timestamptz` (`$table->timestampsTz()`, `softDeletesTz()`). DB session timezone `Europe/Madrid` (`config/database.php` pgsql `timezone`). |
| Primary keys | `bigint generated by default as identity` (`$table->id()`), except `captures` and `attachments`, which use ULID (`char(26)`, `$table->ulid('id')->primary()`), so download URLs are unguessable. |
| Enums | String-backed PHP enums in `app/Enums`. Each enum column has a `CHECK (col IN (...))` with exactly the enum cases. A Pest test reads `pg_constraint` and asserts each enum's cases equal its CHECK list. |
| Soft deletes | `accounts`, `transfers`, `transactions`, `recurring_templates`. Categories, tags, budgets and hints are hard-deleted (deletion is only allowed when unreferenced). |
| Integrity | Enforced in the database (CHECK, composite FK, triggers), not only in PHP. Every constraint has a raw-insert test in `backend/tests/Database` that expects a `QueryException`. |
| Extensions | `pg_trgm`, `unaccent`, plus `f_unaccent(text)`: an `IMMUTABLE` SQL wrapper `SELECT public.unaccent('public.unaccent', $1)` usable in indexes. Created in M0. |
| Tests | Always on PostgreSQL (`finance_test`), never SQLite. |

### Deferred-constraint testing gotcha

`RefreshDatabase` wraps each test in a transaction that is rolled back, so `DEFERRABLE INITIALLY DEFERRED` triggers would never fire in tests. `tests/Pest.php` registers a global `afterEach` for Feature and Database tests that runs `DB::statement('SET CONSTRAINTS ALL IMMEDIATE')`. PostgreSQL then checks all pending deferred constraints retroactively, so a broken ledger fails the test. Tests that need real commits from two connections (recurring concurrency) use `DatabaseTruncation` instead.

### 3.6 `transactions` (M1; `recurring_occurrence_id` added in M4)

Confirmed ledger only. Drafts never live here.

| Column | Type | Constraints |
|---|---|---|
| `id` | `bigint` identity | PK |
| `type` | `varchar(12)` | NOT NULL, `CHECK (type IN ('expense','income','transfer','adjustment'))` |
| `account_id` | `bigint` | NOT NULL, FK `accounts(id)` |
| `amount_cents` | `bigint` | NOT NULL (signed, see sign CHECK) |
| `date` | `date` | NOT NULL |
| `category_id` | `bigint` | NULL |
| `category_kind` | `varchar(8)` | `GENERATED ALWAYS AS (CASE WHEN type IN ('expense','income') THEN type END) STORED` |
| `description` | `varchar(255)` | NULL |
| `merchant` | `varchar(120)` | NULL |
| `note` | `text` | NULL |
| `origin` | `varchar(10)` | NOT NULL DEFAULT `'manual'`, `CHECK (origin IN ('manual','voice','photo','recurring'))` |
| `transfer_id` | `bigint` | NULL, FK `transfers(id)` ON DELETE CASCADE |
| `transfer_leg` | `varchar(3)` | NULL, `CHECK (transfer_leg IN ('out','in'))` |
| `adjustment_target_cents` | `bigint` | NULL |
| `recurring_occurrence_id` | `bigint` | NULL, UNIQUE, FK `recurring_occurrences(id)` ON DELETE SET NULL (added in M4) |
| `created_at`, `updated_at`, `deleted_at` | `timestamptz` | |

Constraints:
- Sign: `CHECK ((type = 'expense' AND amount_cents < 0) OR (type = 'income' AND amount_cents > 0) OR (type IN ('transfer','adjustment') AND amount_cents <> 0))`.
- Category presence: `CHECK ((type IN ('expense','income')) = (category_id IS NOT NULL))`.
- Category kind: `FOREIGN KEY (category_id, category_kind) REFERENCES categories (id, kind)` (default NO ACTION; ON UPDATE actions are not allowed with generated columns).
- Transfer link: `CHECK ((type = 'transfer') = (transfer_id IS NOT NULL AND transfer_leg IS NOT NULL))`, and `CHECK (type = 'transfer' OR (transfer_id IS NULL AND transfer_leg IS NULL))`.
- `UNIQUE (transfer_id, transfer_leg)`.
- Adjustment target: `CHECK ((type = 'adjustment') = (adjustment_target_cents IS NOT NULL))`.
- Origin: `CHECK (type IN ('expense','income','transfer') OR origin = 'manual')` (adjustments are always manual); `CHECK (origin <> 'recurring' OR type IN ('expense','income'))`.

Triggers:
- `transactions_date_after_opening` (BEFORE INSERT OR UPDATE OF `date`, `account_id`): `NEW.date >= accounts.opening_date`.
- `transactions_account_writable` (BEFORE INSERT, and BEFORE UPDATE OF `account_id`): the account is not archived and not soft-deleted.
- `transfer_legs_balanced`: `CONSTRAINT TRIGGER ... AFTER INSERT OR UPDATE OR DELETE ... DEFERRABLE INITIALLY DEFERRED FOR EACH ROW` on both `transactions` (rows with a `transfer_id`, old or new) and `transfers`. It calls `assert_transfer_balanced(transfer_id)`, which requires:
  - a live transfer (`deleted_at IS NULL`) has exactly two live legs: `out` on `from_account_id` with `amount_cents = -transfer.amount_cents`, and `in` on `to_account_id` with `+transfer.amount_cents`, both with `date = transfer.date`;
  - a soft-deleted transfer has zero live legs.

Indexes:
- `(account_id, date) WHERE deleted_at IS NULL`
- `(date) WHERE deleted_at IS NULL AND type IN ('expense','income')` (reports)
- `(category_id, date) WHERE deleted_at IS NULL`
- `(transfer_id)`
- `(origin, created_at)` (usage metrics)
- GIN trigram: `f_unaccent(lower(coalesce(description,'') || ' ' || coalesce(merchant,'') || ' ' || coalesce(note,''))) gin_trgm_ops`

`FOREIGN KEY (category_id, category_kind) REFERENCES categories (id, kind)`.

Generation lower bound: the generator and the forecast only consider slots due on or after the latest of `starts_on`, `generate_from` and the account's `opening_date`. Slots before that bound (like slots after `ends_on`) are neither generated nor listed, and get no occurrence row. `generate_from` is set to the first day of the current month (never moved back) when a template that already has occurrences changes `frequency`, `day_of_month`, `starts_on`, `ends_on` or `account_id`, and when its account's `opening_date` is moved earlier; so those edits never backfill months before the current month. A slot already due in the current month may still be generated.

### 3.12 `recurring_occurrences` (M4)

The idempotency key required by the TRD (`UNIQUE (template, period)`).

| Column | Type | Constraints |
|---|---|---|
| `id` | `bigint` identity | PK |
| `template_id` | `bigint` | NOT NULL, FK `recurring_templates(id)` ON DELETE CASCADE |
| `slot_month` | `char(7)` | NOT NULL, `CHECK (slot_month ~ '^\d{4}-(0[1-9]|1[0-2])$')` |

## 4. Derived values (never stored)

| Value | Definition |
|---|---|
| Account balance at date D | `opening_balance_cents + SUM(amount_cents)` over live transactions (`deleted_at IS NULL`) of the account with `date <= D`. Current balance uses D = today (Madrid). Future-dated rows count only once their date arrives. Computed by `App\Domain\Ledger\BalanceCalculator` in one grouped query for all accounts. |
| `last_movement_date` | Max `date` of live transactions of the account (any type), or null. |
| `last_adjustment_date` | Max `date` of live `adjustment` rows of the account, or null. |
| `last_updated_on` (RF-32) | For `cash` and `savings_investment`: `last_adjustment_date`, falling back to `last_movement_date`, then `opening_date`. For other types: `last_movement_date`, then `opening_date`. |
| `stale` | `cash`/`savings_investment` with `last_updated_on` older than 30 days. |
| Net worth at D | Sum of the balances at D of every non-deleted account (archived included). Credit cards are naturally negative. |
| Reportable rows | Live `transactions` with `type IN ('expense','income')`. Transfers, card settlements and adjustments never count. A single scope `Transaction::reportable()` is the only way reports read the ledger (arch test). |
| Period | Computed by `App\Domain\Period\PeriodResolver` from `settings.month_start_day`; never stored (see `DECISIONS.md` ADR-003). |

## 5. Ledger invariants checked by `app:ledger:verify` (M1, extended in M3/M4)

1. Every live transfer has two balanced legs (same as the trigger, run over all rows).
2. Every expense/income has a category of the same kind.
3. No live row is dated before its account's `opening_date`.
4. `BalanceCalculator` equals a raw SQL sum per account.
5. (M3) Every `confirmed` draft points to a live or soft-deleted ledger row; every attachment without `transaction_id` belongs to a pending draft's capture.
6. (M4) Every `posted` occurrence has exactly one transaction; every `awaiting_amount` occurrence has exactly one pending draft.

The command exits non-zero and prints each violation. It is used by QA and by the restore drill.
